Phase 1

- 회원가입
- 로그인
- 개인폴더 / 팀 폴더 사용 (공통)
    - 폴더는 여러개의 폴더가 1Depth로 제공될 수 있음
    - 폴더는 또다른 자식폴더를 가질 수 있음
    - 폴더는 별도의 이름을 직접 지정받을 수 있음
    - 폴더는 생성날짜, 수정날짜를 기반으로 정렬될 수 있어야 함
    - 폴더는 “이름 변경 이력”을 가져야 함
    - 폴더는 여러개의 파일을 가질 수 있음
    - 폴더는 권한 여부에 따라 특정 사용자 / 특정 팀에 “공유”될 수 있음.
    - 폴더는 권한 여부에 따라 ‘특정 URL 제공’을 통해 “공유”될 수 있음.
    - 폴더 생성/수정/조회/삭제는 권한별로 동작해야 함
    - 파일은 별도의 이름을 지정받을 수 있음
    - 파일은 생성날짜, 수정날짜를 기반으로 정렬될 수 있어야 함
    - 파일은 “수정이력”을 가지며, 각 히스토리 별로 파일이 저장되어야 함
    - 파일은 권한 여부에 따라 특정 사용자 / 특정 팀에 “공유”될 수 있음.
    - 파일은 권한 여부에 따라 ‘특정 URL 제공’을 통해 “공유” 될 수 있음
    - 파일 생성/수정/조회/삭제 는 권한별로 동작해야 함
    - 폴더는 압축형태로 폴더 전체를 다운로드 할 수 있음
    - 파일은 단일/다중 파일 압축 형태로 다운로드될 수 있음
- 팀폴더 사용 (별도)
    - 사용자는 특정 사용자를 초대, 추가를 기능을 활용, URL을 통해 다른 사용자를 팀 폴더에 초대할 수 있음.
    - 팀 폴더 는 팀 과 동일한 개념을 동작함.
- 보안
    - 파일 업로드 시, 파일은 서버에서 암호화되어 저장되어야 함
    - 파일, 폴더 다운로드 시 파일은 복호화되어 다운로드 되어야함

4. ACL 구현
    - BASE 설계
        - ACL은 아래와 같은 스키마를 가짐을 베이스로 둔다
            - 식별자
            - 접근제어 종류 (ALLOW || DENY)
            - 접근제어 주체 종류 (팀||사용자)
            - 접근제어 주체 식별자 (이 ACL으로 접근제어를 하려는 대상 팀PK || 사용자PK)
            - 접근제어 ObjectID (이 ACL로 보호하려는 Object > 폴더 || 파일 PK)

            (이 ACL이 적용될 팀 || 사용자)
    - ACL 제어 공통
        ```
            - ACL 접근제어 유형은 ALLOW || DENY로 제한
            - ACL에는 PermissionBitMask가 있음. 행위 권한 제어를 의미함.
                - 이로부터, "팀에게는 특정 ACL이, 개인에게 별도의 ACL이 할당되어있을 수 있음"
                    - ex : "팀에게는 READ PermBit ACL이, 개인에게는 MANAGE PermBit ACL이 할당"
                - 이로 인해, 모든 ACL은 "개인에게 할당된 ACL이 팀에게 할당된 ACL보다 우선적용" 함을 원칙으로 함
            - ACL 권한제어 예시
                - 개인 ALLOW / 팀 DENY => ALLOW
                - 개인 DENY / 팀 ALLOW => DENY
                - 팀 A DENY / 팀 B ALLOW => ALLOW
                - 팀 A READ / 팀 B WRITE => WRITE
                - ACL 없음	=> 파일/폴더 리스팅 금지
                - ACL 생성자 DENY 시도	=> 불가능, 알림처리
                - 팀 리더 DENY 시도	=> 불가능, 알림처리
            - 동일 피접근제어대상에 대한 여러개 팀 ACL => ALLOW 우선
                - ex : 사용자 A 가 팀 1,2,3에 소속, 특정 폴더가 1,3 DENY / 2 ALLOW
                - 이경우, ALLOW 가 우선된다.
            - 행동제어
                - 적용된 ACL 중, 가장 높은것을 우선적용한다.
                    - 팀 ALLOW 여러개 + 개인 ALLOW => 개인 ALLOW PermBit
                    - 여러개 팀 ALLOW + 여러개 팀 DENY => 팀 ALLOW 중 가장 높은 bitMask
                    - 팀 ALLOW 여러개 + 개인 DENY => DENY
            
            - 별도 제어사항
                - DENY는 팀 리더에게 걸 수 없음
                - DENY는 ACL 생성자를 대상으로 할 수 없음
                - 개인에 대한 동일한 피접근제어 오브젝트를 대상으로 한 ACL 은 중복선언할 수 없다.

            - 공유 ACL
                - 공유로 ACL이 생성될경우 별도의 boolean으로 처리
                    - 공유 ACL + ALLOW = 공유
                    - 공유 ACL + DENY
                        - 팀에게 공유일경우 ALLOW 대상 팀 소속 멤버에 대해서만 설정 가능
                            - 이 경우, 해당 팀을 대상으로 하는 ALLOW가 먼저 있어야만 허용
                        - 개인에게 공유일 경우 : 만들 수 없음
                - 단, 공유타입일 경우 PHASE1 단계에서는 READ까지만 권한을 강제부여한다.
        ```
    - 폴더 권한 제어(ACL)
        - 폴더 권한 테이블(ACL) 설계 및 도메인 설계
        - 이 단계에서의 "권한 제어" 는 "소유/접근" 만 고려한다. 확장성을 위해 도메인 설계시 "공유" 도 염두에 두나, 구현을 진행하지 않는다.
        
        1) ACL (접근권한의 제어)
		    1 > 권한 자체의 범위, 표현방식을 정할것
		    2 > 권한 생성
                - 개인폴더 생성 시, ACL 소유타입:사용자 + 소유자식별자 데이터 삽입, 특정 사용자에게만 귀속
                - 팀 폴더 생성시, ACL 소유타입:팀 + 팀 식별자 데이터 삽입, 특정 팀에게 귀속
                - 개인/팀폴더 공통 : 하위폴더 생성
                    - 하위폴더 생성 시, 부모폴더의 ACL을 Snapshot, 하위폴더 ACL에 부여하는 방향으로 구현한다.
                        - 특정 폴더에 대한 DENY가 있을 수 있으며, 특정 폴더에 대한 공유가 발생할 수 있으므로 일관성을 위해 상위폴더 권한 상속보다는 폴더별 권한 제어로 수행한다. 
			        - 피접근제어종류(팀||사용자) + 피접근제어식별자 로 접근대상을 제약한다.
                - 공유 타입으로 생성 시, Phase1에서는 "READ" 권한 고정으로 생성한다.
            3> 권한 부여
			    - 팀에 멤버 초대 시 -> 팀 귀속이므로 자동으로 권한이 부여됨
			    - 개인폴더는 개인폴더 자동생성(3-2-1) 시에 자동으로 부여되며, 이 단계에서 공유가 없으므로 권한부여 고려X
                - 단, ACL 부여 시 최소 PermissionBitMask는 BROWSE(리스팅) 임. 이하 권한 지원 안함
            4> 권한 회수
			    - 팀으로부터 멤버 강퇴 시 -> 팀 귀속이므로 자동으로 권한 해제
			    - 개인폴더는 권한 회수가 현시점에서 필요하지 않음
        2) PermissionBitMask (행위제어)
            - 적용된 가장 높은 BitMask를 통해 각 행위 요청 Request 발생 시 검증
                - 폴더를 대상으로 작업 발생 
                    -> 팀폴더일 경우 팀ACL + 개인ACL 모두 검증
                    -> 개인폴더일 경우 개인 ACL 검증
        3) ACL 적용
            - 폴더 리스팅 / 폴더 접근 시, ACL 에 따라서 리스팅되도록 3.폴더 구현에 feature를 추가한다
    - 파일의 권한제어(ACL)
        - 파일권한 테이블, 도메인 설계

6. 권한 제어를 포함한 파일 API
	1) 파일 등록
		- 파일 업로드 API 개발 및 구현
		- 이 시점에서, 파일 도메인 설계 보완 필요. 서버 실제 물리경로를 가지도록 refactor할것.
			- 또한 파일 업로드 상태 등, 파일 작업상태에 대한 테이블/도메인 설계 보완할것.
		- 파일을 서버에 등록 할때에는, 물리경로를 UUID 베이스로 구현
		- 파일 임시경로 업로드 (해당 시점에 Folder ACL로 PermissionBitmask가 "쓰기 이상"인지 검증) ->  UUID FE로 리턴 -> UUID 베이스로 서버 업로드 요청
		  -> 메타데이터 Request추출 후 DB에 저장 -> @Async 특정 서버 물리 경로로 이동 -> @Async, 파일 첫 1KB 암호화해서 헤더 강제로 깨기 + 특이구분자 추가할것 (추후 설계)
			- 중간 작업 실패 시, DB 업로드 상태 "실패"로 전환할것.
		- 동일 파일명 (정확히는, 동일 폴더경로 + 동일 파일명) 을 업로드 할경우, 덮어쓰기로 간주, File Version 처리
			* 이 시점, 파일 히스토리 테이블 설계 및 보완 필요
			- 현재 파일 메타정보를 버전정보에 기록하고, 물리경로도 기록한다.
			- 현재 파일 메타정보를 새로 올라온 메타정보로 덮어치고, 물리경로를 새로 기록한다.
	2) 파일 다운로드
		- 요청 진입 시 FolderAcl로 PermissionBitMask가 "읽기 이상"인지 검증 -> 특이구분자를 구분점으로 암호화로 깬 1KB 복호화 -> Streaming방식으로 파일 리턴
 		- 특정 version 요청시 해당 버전의 UUID를 받아서 처리하도록 구현
	3) 파일 삭제
		- softDelete로 구현, Phase1의 마지막에 실제 삭제 스케쥴 구현

7. 권한의 실 활용
	1) ACL(접근권한의 제어)
		1> 폴더 리스팅, 폴더 진입(특정 폴더를 부모폴더로 두는 하위폴더/파일의 조회) API 진입 시 권한판정을 수행한다.
			- X (이렇게 구현하지 말자) ACL리스트 조회 후 -> JAVA IN검색 혹은 for문 순회
			- O (이렇게 구현하자)
				- 루트폴더 리스팅 : UNION을 통해, 팀/개인 나눠서 UNION ALL 
					- 구현방법 : 개인 + 본인식별자 ACL을 찾고, 피접근제어대상(접근제어적용오브젝트) PK가 parentId가 null인것만 조회
				- 폴더 리스팅 : parentId를 특정 ID로 둔 폴더 식별자 중, 팀 제어 + 팀 식별자 / 개인제어 + 개인 식별자 ACL에 ALLOW가 있는것만 조회
				- 파일 리스팅 : 일단 폴더 내에서는 폴더 우선 조회 -> 폴더 조회해 온 숫자가 pagination count보다 적으면 -> file 조회 별도 API 호출로 구성
					- 이때, Folder조회는 folderId가 선택한 폴더 PK인것들을 조회해오면 된다.
					- 파일은, offset, limit 혹은 lastPk 방식 둘 중 하나로 구현하되, FE에서 명백한 파라미터를 삼아서 제출해야 함.
			
	2) PermissionBitMask(행위에 대한 제어)
		1 > 각 동작에 따른 요구권한을 String[] 혹은 record에 적어두고, 요청 진입 시 분기처리한다.

8. 공유 제어
	- 공유에 따른 ACL 생성 (도메인/테이블은 4,5번 공통사용)
	- 파일 / 폴더 공통
		- 공유 시, 각 오브젝트 타입에 맞는 ACL을 추가한다.
	- 공유받은 파일 / 공유받은 폴더 리스팅
		- 팀에게 공유 / 개인에게 공유 기능을 개발, ACL 대상타입을 팀||사용자 + 식별자로 구성한다.
	- ACL을 조회해 리스팅할 수 있도록 한다.
		- 이때, 사용자의 소속 팀에게 공유된것이 있는지도 확인해야 한다.
